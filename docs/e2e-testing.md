# VS Code GUI E2E Testing

This document records the design, operating model, pitfalls, and operational
notes for the heavy VS Code Dev Containers GUI E2E tests.

These tests are intentionally separate from `checks`. They exercise real VS Code,
the Dev Containers extension, a real desktop session, Docker, VS Code server
installation, lifecycle tasks, GUI forwarding, and terminal integration. They
are too expensive and too sensitive to host virtualization state for the default
`nix flake check` path.

## Entry Points

The default E2E package set is generated by `flake/e2e.nix` from every image
target in `images/default.nix` and every supported GUI session exported by
`tests/e2e/vscode-gui.nix`.

`tests/e2e/vscode-gui.nix` still knows the supported GUI sessions:

<!-- BEGIN GENERATED:e2e-sessions -->

| Session        | Backend | Desktop                      |
| -------------- | ------- | ---------------------------- |
| `x11-i3`       | X11     | LightDM auto-login with i3   |
| `x11-xfce`     | X11     | LightDM auto-login with Xfce |
| `wayland-sway` | Wayland | tty auto-login with Sway     |
| `wayland-kde`  | Wayland | SDDM auto-login with Plasma  |

<!-- END GENERATED:e2e-sessions -->

The E2E attribute name format is:

```sh
e2e-vscode-<image-name>-<session>
```

Examples:

```sh
nix build .#e2e.x86_64-linux.e2e-vscode-nix-x11-xfce
nix build .#e2e.x86_64-linux.e2e-vscode-go-1_25-wayland-sway
nix build .#e2e.x86_64-linux.e2e-vscode-python3-web-wayland-kde
nix build .#e2e.x86_64-linux.e2e-vscode-flutter-wayland-kde
```

The E2E packages are exposed under `e2e.${system}`. Do not add them to
`packages.${system}` or `checks.${system}` unless the CI policy explicitly
changes.

Because `e2e` is a custom flake output, `nix flake check` can warn that `images`
and `e2e` are unknown outputs. That warning is accepted. Keeping E2E under
`e2e.${system}` avoids making the default check path evaluate or traverse these
heavy VM tests.

## Timeout Model

The base timeout values in `tests/e2e/vscode-gui.nix` are tuned for a fast local
host. The test exposes a timeout multiplier:

```nix
DEVCONTAINERS_NIX_E2E_TIMEOUT_SCALE
```

The current default scale is `8`, which is the CI/slow-builder profile. With the
375-second base script budget, the default global VM test timeout is 3000
seconds. A local fast run can override it:

```sh
DEVCONTAINERS_NIX_E2E_TIMEOUT_SCALE=1 nix build --impure .#e2e.x86_64-linux.e2e-vscode-python3-wayland-sway
```

The `--impure` flag is required because pure flake evaluation does not read
environment variables. Without `--impure`, the default scale is used.

Important timeout boundaries:

| Step                                 |       Base Budget |
| ------------------------------------ | ----------------: |
| Whole VM test script                 |              375s |
| Docker daemon readiness              |               30s |
| `docker load` inner timeout          |              180s |
| `docker load` wrapper command        |              210s |
| VS Code launch command               |               20s |
| Dev Containers log discovery         |               60s |
| X11 VS Code window detection         |               90s |
| Sway Wayland socket detection        |              120s |
| Sway VS Code window detection        |              180s |
| KDE Wayland session/window detection |              180s |
| Command Palette reopen attempt       | 60s, two attempts |
| Container lifecycle wait             |              120s |
| VS Code GUI ready wait               |               90s |
| VS Code terminal probe               |               60s |
| Container verification               |              180s |
| Artifact collection commands         |        30s or 60s |
| Individual smoke command             |               30s |

These values are multiplied by `DEVCONTAINERS_NIX_E2E_TIMEOUT_SCALE`. Polling
intervals such as one- or two-second sleeps stay unscaled; they are cadence, not
budgets. Scaling them would make failures slower to observe without increasing
the useful wait budget.

The NixOS test timeout covers the VM test script. It does not cover dependency
build time such as generating the Docker archive derivation.

## Host Requirements

The VM requires usable host KVM. The test intentionally does not fall back to
TCG because image import and VS Code startup become too slow to be useful.

Before `start_all()`, the test opens `/dev/kvm`, checks the KVM API version, and
calls `KVM_CREATE_VM`. This catches common host issues earlier than QEMU's
generic connection reset:

- `/dev/kvm` is missing.
- The Nix build user cannot read or write `/dev/kvm`.
- Nested virtualization is disabled.
- Another hypervisor is holding KVM. This was observed with VirtualBox; stopping
  the other VM/process restored KVM.

If this preflight fails, fix the host before debugging VS Code or Docker.

## Image Loading

The test does not call the normal `load-*` apps. The E2E path owns its own image
loading flow:

1. A Nix derivation runs `skopeo --insecure-policy copy nix:<oci-path>
docker-archive:<archive>:<image-ref>`.
2. The VM test receives the resulting Docker archive from the Nix store.
3. Inside the VM, Docker imports it with `docker load -i <archive>`.
4. The test checks `docker image inspect <image-ref>`.

This keeps image conversion outside the VM test timeout. It also made repeated
local runs faster than doing `skopeo copy nix:<oci-path>
docker-daemon:<image-ref>` inside the VM.

The likely reasons are:

- `docker load` streams a Docker archive directly to the daemon, while the
  `docker-daemon:` transport has more conversion and daemon API overhead.
- The archive derivation can be built and cached separately from the VM run.
- VM runtime disk pressure is lower because the expensive conversion scratch
  space is outside the VM.

The disk cost is still significant. In one `python3` run, the prebuilt archive
was about 4.6 GiB in the Nix store and Docker reported about 10.22 GiB after
loading the image into the VM daemon. A `docker-daemon:` copy can also need
temporary conversion space in addition to the daemon graph.

Mounting a `/nix/store` path into the VM is not a replacement for loading the
image. VS Code Dev Containers asks the Docker daemon for an image by tag. The
daemon needs image metadata, layer records, and content in its own graph under
`/var/lib/docker`. A nix2container store path is not a Docker daemon image graph,
and mounting it does not make `docker image inspect <image-ref>` succeed.

## VS Code Fixture

Each VM provisions:

- Docker daemon.
- User `alice`, uid 1000, in the `docker` group.
- `vscode-with-extensions` with only
  `ms-vscode-remote.remote-containers`.
- `/home/alice/workspace/.devcontainer/devcontainer.json`.
- `/home/alice/.config/Code/User/settings.json`.
- A cached VS Code server tarball from `pkgs.vscode.passthru.vscodeServer`.

The VS Code settings disable update, telemetry, workspace trust prompts,
extension recommendations, and online server downloads. The server download base
URL points at an unreachable local address so a cache miss fails loudly instead
of silently using the network.

The generated `devcontainer.json` uses the loaded image tag and sets:

```json
{
  "workspaceFolder": "/workspaces/workspace",
  "updateRemoteUserUID": false
}
```

It also sets a `postAttachCommand` that creates an
`E2E-READY-MARKER.txt` file in the workspace. The file name is base64-decoded at
runtime instead of appearing literally in the command string. That avoids a
false OCR success caused by reading the terminal text that prints or executes
the command.

## Desktop Sessions

All sessions launch VS Code as `alice` with the workspace path:

```sh
code <common-flags> <session-flags> /home/alice/workspace
```

Common flags disable workspace trust, telemetry, updates, release notes, and
password-store integration. The session-specific behavior is:

| Session        | Startup                                                      | VS Code Window Detection        |
| -------------- | ------------------------------------------------------------ | ------------------------------- |
| `x11-i3`       | `machine.wait_for_x()`, merge Alice's Xauthority             | `xdotool` visible window titles |
| `x11-xfce`     | `machine.wait_for_x()`, merge Alice's Xauthority             | `xdotool` visible window titles |
| `wayland-sway` | wait for `/run/user/1000/wayland-*` and `/tmp/sway-ipc.sock` | `swaymsg -t get_tree`           |
| `wayland-kde`  | wait for SDDM, Wayland socket, Plasma user targets           | `kdotool` window titles         |

Sway and KDE use `virtio-gpu-pci`. Sway sets `WLR_RENDERER=pixman` for a more
predictable software-rendered Wayland session inside the VM.

GNOME Wayland was tried earlier but replaced by KDE. In VM runs it could stop at
a non-active display state before the desktop was usable. KDE with `kdotool`
gave a simpler and more scriptable title-inspection path.

## Opening The Dev Container

The primary path is the real VS Code GUI:

1. Open the workspace with VS Code.
2. Open the Command Palette.
3. Run `Dev Containers: Rebuild and Reopen in Container`.
4. Wait for Docker to show a container created from the target image.

The "Attach to Running Container" path is intentionally outside this test. It
exercises a different user flow, adds another Command Palette automation path,
and can hide failures in the primary "open this workspace as a devcontainer"
workflow.

The reopen command uses "Rebuild and Reopen" rather than the shorter "Reopen in
Container" command. The shorter query can match multiple Dev Containers commands
depending on extension state and timing. The longer command title is more
specific and makes the first Command Palette result the intended command.

## `run_command_palette` Rules

`run_command_palette(command, screenshot_name, open_delay, match_delay)` exists
because direct key sequences are fragile when every call reimplements the
timing. It always:

1. Dismisses overlays with `Esc`.
2. Sends `Ctrl+Shift+P`.
3. Waits for the palette to open.
4. Types the provided command text.
5. Waits for filtering to settle.
6. Takes a screenshot.
7. Presses `Enter`.

Command selection follows these rules:

- Pass the full VS Code command title, not a short fragment.
- Case does not matter; VS Code filters case-insensitively.
- The typed string should make the first result the target command.
- Prefer a command title that is unique across the current extension state.
- Keep the command text stable and human-readable; do not depend on command IDs
  unless the UI explicitly displays them.
- Capture a screenshot before pressing `Enter`; if the wrong command is first,
  the artifact must show it.
- Use shorter delays only when the command text is specific enough that a slow
  filter update still converges to the same first item.

Current calls:

| Purpose           | Command Text                                               | Delay                 |
| ----------------- | ---------------------------------------------------------- | --------------------- |
| Open devcontainer | `dev containers: rebuild and reopen in container`          | 3s open, 3s match     |
| Terminal probe    | `terminal: create new terminal in editor area to the side` | default helper delays |

The terminal command intentionally opens the terminal in the editor area to the
side. This gives a more predictable focus target than the panel terminal in the
tested desktops.

## Readiness And Failure Detection

The test does not treat OCR alone as the source of truth.

The GUI ready condition is:

1. The VS Code window title indicates
   `workspace [Dev Container: ...] - Visual Studio Code`.
2. The title does not contain transitional or failure words such as opening,
   connecting, installing, retry, failed, error, or reload.
3. OCR sees the post-attach marker file name in the workspace Explorer.
4. The condition is stable for three samples.

Additional OCR signals are collected for diagnostics:

- `Connecting to Dev Container` means VS Code is still loading.
- `Retry` or `An error occurred` means visible failure.
- `EXPLORER`, `WORKSPACE [DEV CONTAINER: ...]`, and `.devcontainer` show the
  Explorer is rendering the remote workspace.
- `Done. Press any key to close the terminal.` is useful evidence but not a
  required success condition. Some successful runs do not display it at the
  moment OCR is sampled.

The test also scans Dev Containers extension logs for failure patterns. This is
what prevents known failures, such as a VS Code server install/cache failure,
from waiting until the global timeout.

After the GUI is ready, the test opens a VS Code terminal through the Command
Palette and types a simple command that writes files in `/tmp`. The host then
uses `docker exec` to read those files. This proves that the terminal created by
the GUI is a container terminal with:

- user `vscode`
- current directory `/workspaces/workspace`
- the expected command output

This probe is intentionally separate from `docker exec` verification. A plain
`docker exec` proves the container contract; the terminal probe proves VS Code
created a working remote terminal in that container.

## Container Contract Verification

The final verification script runs inside the container and checks the image and
VS Code integration contract:

- `id -un` is `vscode`.
- `HOME` is `/home/vscode`.
- `XDG_RUNTIME_DIR` is `/run/user/1000`.
- `/workspaces/workspace` exists.
- `/usr/share/devcontainer/tasks.json` exists.
- `/usr/share/devcontainer/vscode/extensions-index.json` exists.
- `nix --version` works.
- `devpkg list` works.
- `devcontainer-task-runner status` works.
- Core lifecycle task status files are `done`.
- The post-attach marker exists.
- The VS Code terminal probe files exist and contain the expected values.
- The `gui-env-refresh` task log reports the expected backend.
- `/run/user/1000/devcontainer-gui-env.sh` contains the expected session
  exports.
- The `e2e-baseline` tag from the image's own smoke plan passes inside the
  container.

The lifecycle wait before GUI readiness is narrower than final verification. It
waits for the workspace, shared devcontainer files, and `gui-env-refresh`. It no
longer gates GUI readiness on every lifecycle task. Full lifecycle status is
still checked during final container verification.

For GUI forwarding, the test reads the `gui-env-refresh` task log. It does not
run `devcontainer-gui-env` manually during verification because doing so would
refresh state and could hide the state that VS Code actually produced.

## Artifacts

On success and failure, the test tries to copy `/tmp/e2e-artifacts` out of the
VM. Important artifacts include:

| Artifact                               | Purpose                                        |
| -------------------------------------- | ---------------------------------------------- |
| `vscode-opened.png`                    | VS Code opened the local workspace             |
| `command-palette-reopen-attempt-*.png` | Command Palette command selection              |
| `devcontainer-explorer-ready.png`      | Explorer after GUI readiness                   |
| `devcontainer-terminal-probe.png`      | Terminal after typed probe command             |
| `failure-state.png`                    | Best-effort screenshot on failure              |
| `docker-ps.txt` / `docker-images.txt`  | Docker daemon state                            |
| `docker-inspect.json`                  | Created container details                      |
| `container-logs.txt`                   | Container logs                                 |
| `image-load.log`                       | Archive size, disk state, `docker load` output |
| `vscode-launch.log`                    | VS Code launch output                          |
| `vscode-window-titles.txt`             | Last window-title probe                        |
| `vscode-gui-ready.log`                 | GUI readiness samples                          |
| `vscode-screen-ocr.txt`                | Last OCR text                                  |
| `command-palette.log`                  | Reopen attempt log                             |
| `terminal-probe.log`                   | Terminal probe attempt log                     |
| `container-verification.log`           | Final container contract output                |

| `devcontainers-global-storage.tar.gz`  | Dev Containers extension state                 |
| `vscode-server-tree.txt`               | Remote server directory discovery              |

If a run times out, inspect the screenshot and the matching log first. If the
screenshot looks successful, inspect `vscode-gui-ready.log`,
`vscode-screen-ocr.txt`, `terminal-probe.log`, and
`container-verification.log` to identify which explicit readiness gate failed.

## Debugging History

The current design came from several failed approaches. Keep these notes when
changing the tests; they are practical constraints, not theoretical concerns.

### Missing CA Bundle During Image Build

An early run failed while building an image filesystem because a CA certificate
path did not exist. That was not a VS Code problem; the image derivation itself
must build before the E2E VM starts. E2E failures before the NixOS test driver
usually belong to the image compiler or package dependency graph.

### Generated Test Script Indentation

The NixOS test script linter caught invalid Python syntax when a generated
session snippet escaped the surrounding `try` block indentation. Generated
Python snippets must be indented at the Nix boundary, and lint failures should
be treated as test-definition bugs before running a VM.

### KVM Connection Reset

QEMU once failed with `Connection reset by peer` even though `/dev/kvm` existed,
nested virtualization was enabled, and permissions looked correct. The cause was
another hypervisor using KVM. The preflight now performs `KVM_CREATE_VM` and the
error message explicitly mentions VirtualBox and similar processes.

### Timeouts Masking Fast Failures

Several real VS Code failures originally waited until the global timeout. The
test now checks extension logs and visible failure prompts during waits. If VS
Code reports retry, connection failure, server install failure, or an error
prompt, the test should fail immediately and collect artifacts.

### VS Code Server Cache

When the VS Code server cache was wrong or missing, VS Code attempted server
setup and could fail late. The fixture now preloads the server tarball from
`pkgs.vscode.passthru.vscodeServer`, configures the server download folder, and
uses an unreachable download base URL so accidental network fallback is visible.

### `code --list-extensions` In The Container

The `code` command inside a Dev Containers remote environment can report that it
is only available in WSL or inside a VS Code terminal. It is not a stable
container-side readiness probe. The test now relies on files, logs, window
state, and Docker inspection instead.

### GNOME Wayland

GNOME Wayland could fail before the desktop became active, including screenshots
showing the display output as inactive. It was replaced with KDE Wayland. KDE
keeps a full Wayland desktop case while allowing window-title inspection through
`kdotool`.

### KDE And Optional Terminal Text

KDE runs showed that the VS Code terminal text
`Done. Press any key to close the terminal.` is a strong success signal when it
exists, but it is not guaranteed to be visible when sampled. It must not be the
only readiness requirement.

### Xfce GUI Forwarding Evidence

In Xfce, the visible environment did not always show the expected GUI forwarding
"trace" when inspected by ad-hoc commands. The reliable evidence is the
`gui-env-refresh` task log and the generated
`/run/user/1000/devcontainer-gui-env.sh`, both produced during the VS Code
lifecycle.

### Command Palette Ambiguity

Short Command Palette queries can select different first results across
sessions or extension states. This caused unnecessary instability. The helper
now receives full command titles, and the Dev Containers path uses
`Dev Containers: Rebuild and Reopen in Container` to make the first match the
target command.

### Post-Attach Marker Escaping

The marker file was introduced to prove that VS Code reached `postAttachCommand`
and that the workspace Explorer displays container-side content. Plain string
escaping was fragile, and putting the marker name literally in the command text
could create false OCR hits from the terminal. The current command base64-decodes
the marker name at runtime.

### Terminal Probe Complexity

The terminal probe went through overly complex file and OCR combinations. The
current model is simpler: create a new terminal in the editor area, type a small
command, then use `docker exec` to read the files it created. This keeps the GUI
path real while making the final assertion file-based.

## Maintenance Rules

- Keep the E2E outputs out of `checks` unless CI explicitly opts in.
- Do not add a secondary attach fallback unless the tested user flow changes.
- Do not rely on OCR alone for success.
- Do keep OCR screenshots and text artifacts; they are valuable diagnostics.
- Do not manually refresh `devcontainer-gui-env` during verification; read the
  lifecycle log.
- Keep Command Palette strings full and specific.
- Keep timeout budgets scaled, but leave polling cadence unscaled.
- Add a desktop only if it has a reliable window-title probe.
- Prefer failing on explicit VS Code or Dev Containers errors over waiting for a
  broad timeout.
